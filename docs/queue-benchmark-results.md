# Queue benchmark measurements (TASK-129.6)

Reference host: Apple M1 Max, 32 GiB, macOS arm64, 2026-09-23. Run `mise run queue-benchmark` for the fixed, deterministic Go fixtures and sample quantiles. The runner reports nearest-rank p50/p95/p99; 20 samples except SQLite (3, because each run populates 10,000 records). Subprocess peak RSS includes the Go test process and fixture setup; it is **not** a standalone TUI RSS measurement. Time is Update+View, not physical terminal input-to-paint. GitHub is an in-process fake GraphQL service with 5 ms per data page; request and response totals exclude authentication. The target's render boundary is the Bubble Tea renderer's PTY output, not pixels displayed by a terminal emulator. Physical display paint cannot be timed by a headless PTY and is not claimed. Fixture timings and scope are specified below; do not extrapolate them to production network conditions.

A phase-separated five-source refresh benchmark (three runs of five iterations each, on D22) attributes most synchronous input-loop time to the sorted view projection: at 10k/50k/100k items, snapshot cloning took roughly 4/25/55 ms and projection roughly 48/346/795 ms per operation. Projection allocated roughly 46/261/525 MB per operation. These phase timings are diagnostic microbenchmarks, not end-to-end percentiles. They are included in the local runner and relative CI comparison to distinguish clone costs from sorting/filtering costs when addressing the refresh stall. The benchmark runs against the full source snapshot; a warm navigation measurement cannot capture this cost.

The production publisher now clones each snapshot on its worker before handing it to the Bubble Tea event loop. Five D22 samples of the prepared 50,000-summary refresh still measured p50/p95/p99 366.60/379.71/379.71 ms (Update+View only), allocating ~261 MB per operation. The local runner and relative CI also track prepared 10k/50k/100k refreshes. This removes producer snapshot cloning from the input loop, but **does not** meet the 50 ms concurrent-refresh budget: projection still runs synchronously. The original full-refresh benchmark below uses the unprepared message path and remains as a diagnostic baseline. The prepared path now also sorts source-visible keys on the worker, then filters and deduplicates against the current snapshot on the event loop, preserving newer claim observations. Three five-iteration D22 runs of 50,000-summary prepared refresh Update+View measured 78.62, 97.25, and 84.04 ms/op, allocating about 49 MB/op; these are run means, **not** p50/p95/p99 or terminal paint. A PTY-backed Bubble Tea renderer probe (`QUEUE_TERMINAL_SAMPLES=20 go test ./internal/queueui -run '^TestQueueTerminalOutputLatency$' -v -count=1`) measures from a keyboard byte written to a local pseudoterminal until the updated selected-row marker appears in the renderer's PTY output. On D22, 20 alternating j/k samples at 10k/50k/100k yielded p50/p95/p99 16.48/17.59/17.61, 16.67/17.49/17.64, and 16.70/17.34/17.53 ms. When a separately prepared full snapshot was sent immediately before each input (a distinct marker in each new snapshot proves the fresh frame was observed), the corresponding times from publication through input and output were 8.32/11.95/21.16, 43.09/48.51/48.51, and 81.78/87.50/88.00 ms. Preparation and provider/index work are excluded; publishing before writing the key does not prove the event loop processed them in that order. The PTY captures renderer output, **not physical terminal display paint**. These figures do not establish the full input-to-paint or combined-fault budgets; the 100k refresh-output boundary exceeds 50 ms. The probe is opt-in and does not impose absolute CI thresholds.

A separate opt-in combined-pressure probe (`QUEUE_COMBINED_SAMPLES=20 go test ./internal/queueui -run '^TestQueueCombinedFaultOutputLatency$' -v -count=1`) drove a real PTY renderer at 50,000 summaries while publishing worker-prepared full refreshes, marking one source rate-limited, holding a read indefinitely, recomputing a 50,000-node dependency chain on another goroutine, and renewing a real local Worklease claim concurrently. On D22, 20 samples from refresh publication plus keyboard input to the distinct selected-row bytes yielded p50/p95/p99 40.24/52.93/53.43 ms; local renewal latency was 1.19/1.27/1.45 ms and minimum previous-lease margin at completion 9m59.35s for a 10-minute TTL. A follow-up D22 20-sample run drove two real GitHub adapter instances through fake HTTP: one returned 429 with Retry-After 60 seconds, and subsequent List calls were refused by its quota gate without further HTTP traffic (one rate HTTP request total); the other kept a request in flight until its context was canceled (one stalled HTTP request total). The simulated GitHub server and shell-token fixture do not reproduce a production subprocess failure, and graph recomputation remains in memory; the claim uses a local SQLite authority. This run measured publication plus input to PTY output p50/p95/p99 39.36/48.93/50.12 ms, renewal 0.76/1.18/1.19 ms, and minimum prior-lease margin 9m59.26s. The prior simulated-only run above measured p95 52.93 ms. Both probes capture PTY bytes rather than physical display paint, and preparation is outside the timed input window. They demonstrate renderer and local renewal progress under these fixture pressures, **not** the complete combined-fault acceptance or a reliable 50 ms p95 guarantee. A further D22 20-sample run added real `queueindex.Index.Replace` of 10,000 source summaries on a separate goroutine during each 50,000-summary refresh, alongside the HTTP rate-limit/stalled-read fixture, 50,000-node graph recomputation and local claim renewal. Publication plus keyboard input to PTY output p50/p95/p99 was 49.26/56.09/56.63 ms; index replacement 21,633/23,413/23,570 ms, resulting SQLite database plus WAL/SHM 26,878,160 bytes; renewal 1.16/3.22/73.47 ms with a minimum prior-lease margin of 9m36.39s at 10-minute TTL. One rate-limited request and one stalled request occurred, with the rate gate refusing additional requests. `/usr/bin/time -l` reported 1,118,486,528 bytes peak RSS for the **Go test process**, which includes fixture graph, snapshots, HTTP server, index and renderer rather than a standalone queue client. The 20 repeated full index replacements are an intentionally heavy synthetic load, not the production incremental scheduler or simultaneous provider-to-index update. PTY output still excludes physical display paint; p95 exceeds the provisional 50 ms concurrent-refresh target. Do not infer end-to-end safety or memory-budget compliance from this test. Repeat with the production provider/index scheduler and physical terminal paint before closing §14.

A separate opt-in cold first-page renderer probe (`QUEUE_COLD_PAGE_SAMPLES=20 go test ./internal/queueui -run '^TestQueueColdPageOutputLatency$' -v -count=1`) uses the real GitHub adapter against a 5 ms/page fake HTTP service, then publishes only the first 100 of 10,000 summaries to a running Bubble Tea PTY renderer. D22 20-sample request-to-PTY-output p50/p95/p99 was 16.65/17.50/17.56 ms; after the adapter returned the first page, publication-to-output was 10.46/11.29/11.33 ms. There was one data request per sample, 236,480 response bytes total (11,824 per page), zero additional enumeration requests. Authentication/resolve occurred before timing. The renderer was already started; this excludes initial startup, production index publication, and physical display paint, so the cold remote 150 ms end-to-end budget remains unverified. The first page was re-requested on each sample rather than paginating the source.
