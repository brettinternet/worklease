The Backlog.md runner (`scripts/queue-backlog-benchmark.py`) measured 20 read-only samples on the pre-existing deterministic 10,000-task fixture, using the real Backlog.md CLI. Each list used one child process, zero provider API requests, 5,486,861 bytes of local stdout/stderr, and zero remote quota; p50/p95/p99 were 2,133 / 2,420 / 2,476 ms. A selected task view (edge read) used one process, 4,216 output bytes, and p50/p95/p99 1,878 / 2,109 / 2,181 ms. The two commands together peaked at 327,073,792 bytes child RSS (peak across subprocesses, not simultaneous memory), and fixture Markdown occupied 1,578,206 bytes. The Go TUI and Backlog child process must be accounted for separately; exhaustive 10,000-item cold edge reads remain impractical. `mise run queue-benchmark` creates and retains a fresh temp fixture unless `QUEUE_BENCH_FIXTURE` names an existing one; CI runs the same relative-only comparison with three samples.

A phase-separated five-source refresh benchmark (three runs of five iterations each, on D22) attributes most synchronous input-loop time to the sorted view projection: at 10k/50k/100k items, snapshot cloning took roughly 4/25/55 ms and projection roughly 48/346/795 ms per operation. Projection allocated roughly 46/261/525 MB per operation. These phase timings are diagnostic microbenchmarks, not end-to-end percentiles. They are included in the local runner and relative CI comparison to distinguish clone costs from sorting/filtering costs when addressing the refresh stall. The benchmark runs against the full source snapshot; a warm navigation measurement cannot capture this cost.

The production publisher now clones each snapshot on its worker before handing it to the Bubble Tea event loop. Five D22 samples of the prepared 50,000-summary refresh still measured p50/p95/p99 366.60/379.71/379.71 ms (Update+View only), allocating ~261 MB per operation. The local runner and relative CI also track prepared 10k/50k/100k refreshes. This removes producer snapshot cloning from the input loop, but **does not** meet the 50 ms concurrent-refresh budget: projection still runs synchronously. The original full-refresh benchmark below uses the unprepared message path and remains as a diagnostic baseline. The prepared path now also sorts source-visible keys on the worker, then filters and deduplicates against the current snapshot on the event loop, preserving newer claim observations. Three five-iteration D22 runs of 50,000-summary prepared refresh Update+View measured 78.62, 97.25, and 84.04 ms/op, allocating about 49 MB/op; these are run means, **not** p50/p95/p99 or terminal paint. The 366.60/379.71/379.71 ms figures above are the pre-ordered baseline. Filtering and counting still exceed 50 ms, so concurrent-refresh and combined no-freeze criteria remain unmet. Neither path measures physical terminal paint. A further phase split of the worker-prepared refresh (`go test ./internal/queueui -run '^$' -bench '^BenchmarkQueuePreparedRefreshEventLoop/items-' -benchtime=5x`) measured Update versus cached View separately on D22: 10k 13.64/0.32 ms, 50k 97.01/1.19 ms, 100k 214.56/2.05 ms (five-iteration means; the Update phase allocates ~12/60/119 MB). Worker preparation was excluded. A subsequent single-pass standard-view count change reduced two eight-iteration 50k Update means to 71.61 and 70.18 ms/op (~55.6 MB/op), from the prior 97.01 ms/op (~60 MB/op); configured views still use the original count path. A subsequent worker-prepared default All projection avoids rebuilding its ordered row slice on the input loop; newer claim observations patch the prepared rows before display, while filtered/configured views retain the current-snapshot fallback. Two 12-iteration D22 runs of 50k prepared Update measured 38.16 and 39.54 ms/op (4.42 MB/op), versus the prior ~70 ms/op (55.6 MB/op). Source preparation allocates an extra row slice and is excluded from refresh timings but included in process peak RSS. No result measures concurrent provider/index load or physical terminal paint. The 50 ms concurrent-refresh budget remains **unverified**, and the combined no-freeze criterion is still open.

A PTY-backed Bubble Tea renderer probe (`QUEUE_TERMINAL_SAMPLES=20 go test ./internal/queueui -run '^TestQueueTerminalOutputLatency$' -v -count=1`) measures from a keyboard byte written to a local pseudoterminal until the updated selected-row marker appears in the renderer's PTY output. On D22, 20 alternating j/k samples at 10k/50k/100k yielded p50/p95/p99 16.48/17.59/17.61, 16.67/17.49/17.64, and 16.70/17.34/17.53 ms. When a separately prepared full snapshot was sent immediately before each input (a distinct marker in each new snapshot proves the fresh frame was observed), the corresponding times from publication through input and output were 8.32/11.95/21.16, 43.09/48.51/48.51, and 81.78/87.50/88.00 ms. Preparation and provider/index work are excluded; publishing before writing the key does not prove the event loop processed them in that order. The PTY captures renderer output, **not physical terminal display paint**. These figures do not establish the full input-to-paint or combined-fault budgets; the 100k refresh-output boundary exceeds 50 ms. The probe is opt-in and does not impose absolute CI thresholds.

A separate opt-in combined-pressure probe (`QUEUE_COMBINED_SAMPLES=20 go test ./internal/queueui -run '^TestQueueCombinedFaultOutputLatency$' -v -count=1`) drove a real PTY renderer at 50,000 summaries while publishing worker-prepared full refreshes, marking one source rate-limited, holding a read indefinitely, recomputing a 50,000-node dependency chain on another goroutine, and renewing a real local Worklease claim concurrently. On D22, 20 samples from refresh publication plus keyboard input to the distinct selected-row bytes yielded p50/p95/p99 40.24/52.93/53.43 ms; local renewal latency was 1.19/1.27/1.45 ms and minimum previous-lease margin at completion 9m59.35s for a 10-minute TTL. A follow-up D22 20-sample run drove two real GitHub adapter instances through fake HTTP: one returned 429 with Retry-After 60 seconds, and subsequent List calls were refused by its quota gate without further HTTP traffic (one rate HTTP request total); the other kept a request in flight until its context was canceled (one stalled HTTP request total). The simulated GitHub server and shell-token fixture do not reproduce a production subprocess failure, and graph recomputation remains in memory; the claim uses a local SQLite authority. This run measured publication plus input to PTY output p50/p95/p99 39.36/48.93/50.12 ms, renewal 0.76/1.18/1.19 ms, and minimum prior-lease margin 9m59.26s. The prior simulated-only run above measured p95 52.93 ms. Both probes capture PTY bytes rather than physical display paint, and preparation is outside the timed input window. They demonstrate renderer and local renewal progress under these fixture pressures, **not** the complete combined-fault acceptance or a reliable 50 ms p95 guarantee. Repeat with production provider/index concurrency and physical terminal paint before closing §14.

The initial uncached TUI navigation benchmark measured p95 147.50 ms at 10,000 and 4,957.92 ms at 100,000. Caching the sorted projection removes repeated full-corpus sorting on each keystroke. A separate 20-sample full-snapshot publication plus View benchmark (same event loop as input, fixed five-source fixture) measured p50/p95/p99 of 54.20/56.20/57.28 ms at 10,000, 359.80/377.27/380.33 ms at 50,000, and 813.49/840.41/852.23 ms at 100,000. During a synchronous full-refresh message, keyboard events can wait at least that long: warm keypress numbers do **not** establish the concurrent-refresh 50 ms budget or the combined-fault no-freeze criterion. The benchmark omits terminal paint and provider fetch; do not substitute it for those end-to-end measurements. The 256 MiB provisional 50,000-summary RSS budget **failed**, so §14 proposes 512 MiB pending end-to-end concurrency validation. The observed 100,000-summary failure boundary is refresh responsiveness and memory growth, not a crash or warm scrolling; true terminal paint and provider/index concurrency remain unmeasured. Full cold remote view, terminal paint, combined fault/refresh scenario, production GitHub quota costs, and renewal margin remain open.
