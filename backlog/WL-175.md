WL-172 settled that a harness-supplied session ID, not new attributes, is how a claim traces back to the agent session that held it. The guidance doesn't say so: worklease instructions loop step 3 (internal/instructions/instructions.go) and skills/worklease-workflow/SKILL.md mention only a harness loop-run ID, otherwise a generated UUID, so one-shot agents generate random IDs that lead nowhere. Observed 2026-10-23: a Claude Code session claimed WL-172 with a uuidgen value although CLAUDE_CODE_SESSION_ID was set, and a shell-wide WORKLEASE_SESSION_ID held a terminal pane ID that every session in that pane reused. Keep this provider-neutral: name the rule, not a list of harness variables.

## Acceptance criteria

- [ ] worklease instructions loop and skills/worklease-workflow/SKILL.md say to use the harness's own loop-run ID, else its session ID, else a generated full UUID, and give the reason: the claim's sessionId is how people find the session that worked an item
- [ ] The guidance says a delegated worker that claims independently needs its own ID, and that IDs must not come from terminal panes, labels, or other values reused across sessions
- [ ] mise run doc-test passes
