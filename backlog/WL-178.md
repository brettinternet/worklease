## Why

`--wait` is capped at 60s for local and remote acquire (`internal/cli/lease_commands.go`, `internal/cli/remote_lifecycle.go`), but the default TTL is 15m, so a waiter almost always times out before the holder releases. The README quick start (`-w 2m`) and the `acquire --help` example (`--wait 2m`) both fail with `invalid-argument: wait must be between 0 and 60s`.

## Shape

- Raise the CLI cap to 1h, matching the `watch` maximum. Keep MCP `wait` at 60s because tool calls are short.
- Local replay deadlines default to 24h, and the remote client already waits in 30s watch chunks, so neither needs a protocol change.
- Update the docs that state the 60s CLI cap: `docs/remote-claim-authority.md`, `docs/remote-authority-protocol-v1.md`, and `skills/worklease-workflow/SKILL.md`.

## Acceptance criteria

- [ ] Local and remote `worklease acquire --wait 2m` is accepted, as the README and acquire help examples show; waits above 1h fail with invalid-argument
- [ ] MCP acquire still rejects wait above 60s
- [ ] A local and a remote waiter blocked past the old 60s bound acquire once the holder releases within the wait
- [ ] Docs and the worklease-workflow skill state the new CLI cap; `mise run doc-test` passes
