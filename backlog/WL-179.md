## Why

`worklease run -r KEY -- CMD` fails immediately with `already-claimed` when another worker holds KEY, and it rejects `-w`. Serializing a command on a shared resource (`deploy:staging`, an e2e port, a test database) is the main reason to wait, and `run` is the natural command for it:

```sh
worklease run -r deploy:staging -w 30m -- ./deploy.sh
```

With `--detach`, an agent can get in line without holding a tool call open past its harness timeout, then collect the result with `runs wait ID`. That covers the practical need behind a FIFO wait queue without server-side queue state.

## Shape

- Add `--wait/-w` to `run` and pass it to the run's internal acquire, with the same bounds as `acquire --wait`.
- A detached run waits in its background supervisor under a visible waiting state.
- Grant order stays whichever waiter polls first, not FIFO. Fair queues stay in WL-168 until starvation is observed.

## Acceptance criteria

- [ ] `worklease run -r KEY -w D -- CMD` starts CMD after the holder releases within D; otherwise it exits with wait-timeout without starting CMD
- [ ] A detached run that is waiting shows a waiting state in `runs` and `runs show`; `runs wait` blocks through the wait and the worker
- [ ] Cancelling a waiting run, by interrupt or `runs stop`, starts no worker and leaves no claim held
- [ ] The CLI reference and worklease-workflow skill show serializing a command on a shared resource with `run --wait`; `mise run doc-test` passes
