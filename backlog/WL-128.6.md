Agents need the queue's information without screen scraping, and no workflow may be safer in the TUI than in automation (plan section 13). Each item must carry its exact claim resources and key inputs, so a CLI caller acquires the same bytes the queue would (plan section 6).

The command builds sources from queue.yaml through the WL-128.3 adapter registry, so it works with whichever built-in adapters are registered; tests use the fake adapter. `--max-age` belongs to WL-129.1 because it needs the index, and `queue next` belongs to WL-130.4. This task owns the command, its JSON schema v1, and its documentation.

## Acceptance criteria

- [x] `worklease queue query --view NAME --json` emits one versioned envelope. It contains the view; the authority (profile, authorityId, and local or remote scope); per-source coverage, freshness, and diagnostics; and items. Each item has ref, display ID, title, raw and normalized state, readiness with reasons, provider-reported readiness, assignment, claim observation, native claim state, `resources`, `keyInputs`, and per-action availability with reasons
- [x] `resources` and `keyInputs` are byte-identical to `worklease key` output for the same inputs, as tested against the WL-126.4 vectors
- [x] `--limit` and an opaque `--cursor` give bounded pagination. The cursor is bound to view, query, sort, sources, principal, and generation, and any mismatch (changed filter, changed credential scope, stale generation) returns a structured cursor error
- [x] `--require-complete` exits non-zero with a structured `incomplete` result when source coverage or dependency edges are incomplete
- [x] Without `--json`, the command prints a compact human-readable table consistent with existing list output
- [x] Output passes through the existing internal/output normalization and redaction
- [x] The command is covered by the help, man-page, and zero-flag audit tests like other commands, and docs/queue.md and docs/cli-reference.md document it and its JSON schema
