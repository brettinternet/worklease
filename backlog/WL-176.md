## Why

WL-172 settled that a claim traces back to its agent session through the harness session ID, not new attributes, and WL-175 updated the guidance to prefer that ID. Two gaps remain for anyone reading claims directly (`worklease status`, `list`, the claims TUI):

- **Decorated IDs.** Callers still decorate the ID. On 2026-10-29, bl's BL-136 was claimed as `claude-1deede08-…` while that session's `CLAUDE_CODE_SESSION_ID` was `1deede08-…`. Herdr (`herdr agent list` → `agent_session.value`) and Claude Code (`~/.claude/sessions/*.json` → `sessionId`) match only the exact ID, so a decorated ID can't be looked up.
- **`agentId` is the login user.** It defaults to the login user, so on one host it never says which agent holds a claim.

This keeps WL-172's decision. It adds no claim fields: callers fill the existing ones consistently. Contact handles (pane, peer name) are resolved from the session ID at read time by readers such as bl, never stored here. Re-raise WL-172's attributes only if a reader needs something that can't be derived from the session ID.

## Shape

- `worklease instructions`, skills/worklease-workflow/SKILL.md, docs/claim-model.md ("To trace a claim back…"), and docs/agent-setup.md: pass the harness ID unchanged, with no prefix or suffix. Set `WORKLEASE_AGENT_ID` (or `--agent`, MCP `agentId`) to the agent kind, such as `claude`, `pi`, or `codex`, keeping it provider-neutral as WL-175 did. `agentId` stays audit identity, never authorization.
- Keep the login-user default for callers that pass nothing.
