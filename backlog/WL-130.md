Humans need to claim work directly from the queue, and agents need a deterministic next-ready selector that does not screen-scrape. The queue then becomes a Worklease client that owns claims. It must use the same handle, session, heartbeat, admission, and recovery rules as the CLI, with no weaker path. See plan sections 5, 6, 9 ("Who renews a claim?"), 13, and 16 (S4), and D5, D11, D12, D23, D24, and D25.

This parent is an integration checklist, not an implementation lane. It depends on every child, so it becomes ready only after they are Done. Complete it by re-verifying the criteria below on main and recording the evidence.

## Acceptance criteria

- [x] Every S4 child task is Done
- [x] A remote authority outage never changes the authority a view uses
- [x] The queue and the CLI contend on byte-identical resources, as shown by an end-to-end contention test in both directions
- [x] The renewal margin holds under the S3 load scenarios
- [x] Native occupancy is never rendered as global exclusion
- [x] `queue next` explains the dependency reasons behind every candidate and every no-work result
- [x] Concurrent agent loops using `queue next --claim` through the CLI or MCP claim distinct items with no wasted selection, as shown by the WL-130.5 and WL-130.6 concurrency tests on main
